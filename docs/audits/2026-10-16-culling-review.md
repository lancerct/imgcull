# imgcull 代码审查与需求适配评估

审查日期：2026-10-16。基线：lancerct/imgcull main，提交 `022c4161302aa29a5a230c0469814507e97e385b`（0.2.8）。PR #1 另行评估，尚未合并。

## 结论与边界

建议有条件继续使用 imgcull，不建议现在重写。它的模块划分、模型接口、RAW 预览提取、命令行和已有测试有价值；主要问题集中在元数据读写及“单张打分后立即写回”的流程。这两部分可以在同一个 Rust 程序内改造，没有理由同时维护第二套 Python 产品流程。

当前版本不适合直接对包含既有调色、RAW/JPG 配对的真实图库运行评分写回。这里的“高风险”主要指调色/标记数据丢失与错误结果，不表示发现了可远程接管电脑的漏洞。

本轮是第一轮源码审查，不是完整安全认证：读取了仓库全部 13 个 Rust 源文件、现有测试、配置和工作流；保留了 41 个文本文件的固定版本快照。没有调用收费模型、没有上传照片、没有修改图库、没有改变模型配置。没有进行完整的依赖漏洞数据库扫描、真实 Lightroom 兼容矩阵或各家模型端到端评测。本机无 Rust 工具链，未在本机编译；已核实 PR #1 对同一 Rust 基线的 GitHub Rust 构建与原测试通过。已有测试通过不代表下面这些边界已被覆盖。

另附 7 个调用项目真实公开接口的调查用 Rust 测试，使用临时合成文件、无需照片和 API。它们断言“旧版本确实呈现该缺陷”，不是生产要求；只能用于审计分支，修复时应改为正确行为的回归测试。执行结果见审计 PR 的 Actions；在确认结果前不称为动态复现。

## 一、必须先修的可靠性问题

### A01 高：同名 RAW/JPG 会竞争同一个 XMP

位置：src/discovery.rs:38、src/xmp.rs:24、src/pipeline.rs:105。

发现机制：扫描按文件返回 photo.NEF 与 photo.JPG；二者均映射为 photo.xmp；每个任务独立读取、分析和写回。默认并发为 4，没有按目标文件排他。两次读到旧状态时，后写入者覆盖先写入者；重复传入文件或目录也没有去重。即使并发改成 1，也只是避免同时写，并未解决同一照片两次分析、原始文件名互相覆盖及重复收费。

对用户影响：这是当前图库的常见组织方式，不是罕见边界。
修复方向：在扫描之后建立“照片实体”，同目录同基名的 RAW/JPG 为一项；显式选定分析输入和唯一元数据目标。不能通过把 RAW 和 JPG 两张原片删掉其中一张来解决。

### A02 高：合法的 XMP 简写形式会被写坏，输出没有再解析验证

位置：src/xmp.rs:444–543、src/xmp.rs:311–319。

具体例子：合法的 `<rdf:Description .../>`，写入会把新属性放在斜线之后；分数等子元素只会插入到 `</rdf:Description>` 前，而简写本来就没有这个结尾。单引号表示的 Rating 读不到，随后写入会产生重复属性。Rating 用子元素表示、或命名空间使用不同前缀，也没有语义层面的统一处理。ensure_namespace 通过全文包含关系判断声明存在，无法保证声明在目标元素作用域内。

对用户影响：原来可用的元数据可能变成 Lightroom 读不了的文件。
调查测试：self-closing、single-quoted 两项。
修复方向：按 XML 命名空间与目标资源识别字段，支持标准合法表示；写前解析验证，并比较未授权字段的语义是否保持。不能只修一个字符串替换位置就宣称支持所有 XMP。

### A03 高：读取失败时丢弃原内容；备份失败也继续覆盖

位置：src/pipeline.rs:119–128、252–268；src/config.rs:230–231。

现有 XMP 读取或解析失败后，程序创建空白 sidecar，后续仍可能覆盖原文件；启用备份时若备份失败只记录错误，仍然写回。默认备份关闭。

对用户影响：一个本来可恢复的旧文件，可能被只剩 AI 字段的新文件替代。
修复方向：该项进入冲突/失败列表并停止写入；备份失败必须阻止写入。继续审阅其他照片可以，不能悄悄重建源元数据。

### A04 高：保存不能检测处理中产生的新编辑，也不支持可靠恢复

位置：src/xmp.rs:73–75、175–176、311–318、597–600。

旧内容在模型分析前读入内存；写入前不检查磁盘是否已变化。如果等待模型期间 Lightroom 保存了新调色，旧内存内容会把它覆盖。fs::write 直接写目标，异常中断可能留下截断文件；备份永远写固定的 .xmp.bak，下次覆盖上次备份；没有每项提交日志与回滚冲突检查。

调查测试：stale-snapshot、second-backup。
修复方向：分离分析与应用；应用前检查哈希/当前内容；独立不可覆盖备份；同目录临时文件完整落盘后替换；逐项记录提交状态；回滚前检查后续用户修改。哈希检查和替换间的竞态仍需考虑，不能声称单靠哈希解决任意并发编辑；应用阶段应避免其他编辑器同时写元数据。

### A05 高：不完整的模型回答会被当成已完成评分

位置：src/llm.rs:181–193、src/scoring.rs:20–44、65–71；src/pipeline.rs:136、225–230。

所有分数字段都是可缺省的，未知字段被忽略。类似 `{"message":"unable to judge"}` 的对象也能解析为评分结果，缺失维度平均成 0，映射为 1 星，写入后 has_scores 为 true，后续默认跳过。只有一项分数时也直接作为总分，没有完整性、拒答或不确定状态。

调查测试：non-score-json。
修复方向：验证必需维度、有限数值和结果状态；拒答/缺图/不确定是独立结果，不是低分。无有效评分时不写星级，不标成完成。输出小数两位不等于判断精度达到百分之一。

## 二、重要的兼容性与运行问题

### A06 中：既有文字会被改变，用户关键词与星级的“所有权”不明确

位置：src/xmp.rs:99–105、139–160、324–353、444–469；src/pipeline.rs:219–230。

读取文字没有进行 XML 实体解码，写入时再次转义，所以 A &amp; B 可变为 A &amp;amp; B；无关的原文件名更新也可能触发这个变化。多语言说明会被缩成单个默认语言。评分成功会替换 dc:subject 关键词，而非在独立字段保存建议；默认会重设星级，即使已有人工评分。部分“替换”属于既定产品行为，不是上游程序失控，但与本用户需求冲突。

调查测试：escaped-caption。
修复方向：保留未修改字段原样/语义不变；人工字段优先；AI 关键词先作为建议，合并或覆盖由明确选项控制。--no-rating 仅停星级，不代表只读。

### A07 中：写入 XML 的模型标识未转义

位置：src/xmp.rs:370–378。

scored_by 来自 provider/model 字符串，直接插入 XML 文本；合法的本地模型别名/配置若包含 & 或 <，会生成非法 XML。
调查测试：model-identifier。
修复方向：所有进入 XML 的文字统一转义，最终整体校验。本例是本地配置导致的文件损坏风险，不应夸大为远程代码执行。

### A08 中：错误被打印，但最终退出状态和统计可能显示成功

位置：src/pipeline.rs:239–268、274–279；src/summary.rs:67–113；src/main.rs:111。

模型失败、写文件失败多数只记录错误；pipeline 最终返回 Ok。分数统计在确认落盘前增加，没有独立“写入失败”计数。无人值守或外层脚本可能以为任务已成功，实际文件没有更新。
修复方向：分别记录分析、审阅、应用、失败；输出可机读结果和失败退出码；允许恢复失败项，不依赖人工翻日志。

### A09 中：扫描边界和并发配置缺少约束

位置：src/discovery.rs:38–100；src/report.rs:106–167；src/pipeline.rs:69、105；src/main.rs:56–58。

目录和直接输入未去重；目录符号链接会被跟随，没有已访问目录集合/范围检查，可能重复、绕出指定根目录或形成循环；NAS 缓存目录没有排除。concurrency=0 会让所有任务等待永远拿不到的许可；过大的数也没有应用层上限。逐文件任务全部创建后等待 semaphore，与严格限制排队任务数不同。

修复方向：规范化照片身份、去重、明确链接策略及缓存排除；拒绝 0 并设置合理并发边界。链接跨界在云模型模式还可能把原本不在预期范围的照片提交出去，需在扫描计划中显式展示。

### A10 待实图验证：方向与细节证据不足

位置：src/preprocessing.rs:67–71、95–104、109–134。

RAW 当前取内嵌预览，不是完整 RAW 显影。大图缩到最长边 2048 后送单图，不能证明 45MP 原图的人眼/鸟眼是否失焦，也不能确定 RAW 高光可恢复程度。重编码路径未见 EXIF 方向应用；具体受影响文件需要方向测试样片确认，暂不算已动态证实。

修复方向：概览与原生细节分层；明确图像方向；技术废片要看实际主体位置的细节；疑难 RAW 进一步解码/用当前显影结果，不可把支持 NEF 扩展名等同于完成 RAW 质量判断。

### 其他待核查点（不包装成已证实漏洞）

请求层没有暴露总超时、取消和本地 num_ctx 参数，但依赖库可能有默认 HTTP 超时，应检查锁定版本再定修复范围。云 provider 的 base_url 配置字段未被 API-key 构造路径使用，容易造成“配置了却没生效”；Ollama 的 base_url 则实际使用。CSV 做了分隔符转义，但未处理电子表格公式开头，导入 Excel 的场景需考虑。小 JPEG 走原字节传递可能保留 EXIF 信息；如需严格去定位信息，应专门定义导出策略。未做供应链漏洞扫描，不能给出“依赖无漏洞”的结论。

## 三、需求能否在它上面实现

| 需求 | 现状 | 建议 |
|---|---|---|
| RAW/JPG 一张照片计数 | 按文件扫描 | 扩展 discovery 的结果结构，保留原片，不建第二个扫描器 |
| 人物好且不同动作都留 | 单图打分 | 增加同组多图比较接口与场景/动作记录，不设保留数量上限 |
| 无好片时选相对最好 | 无组概念 | 在组决策中保留 fallback，而非改平均分阈值 |
| 星空堆栈、括号曝光、全景保护 | 无序列目的记录 | 增加受保护序列和人工纠正入口；不能仅凭时间间隔判废 |
| 红色与绿色含义 | 无对应个人决策字段 | 独立“删除建议/后期建议”与解释，不把红色等同低星 |
| 鸟类行为、展品记录价值 | 通用五项分数 | 按题材规则判断，有独立记录价值可以不标星但保留 |
| 标红前大图/细节复核 | 单张预览 | 增加证据等级和待复核状态，模型未确认时允许弃权 |
| 已有调色、评分保留 | 仅部分字段保留 | 重做可靠的 XMP 合并/事务边界；JPEG-only 独立嵌入方案 |
| 中断续跑与版本追踪 | 有分数就跳过 | 同一程序记录任务、照片组、模型、规则版本、证据、结果和应用状态 |
| 不占屏幕 | CLI 可后台运行 | 保留 CLI，限制 CPU/GPU 并发；不等于完全不影响游戏 |
| Codex 当前模型判断 / Ollama | Rust 程序需自己调用模型 | 可增加导出审阅包与导入决定路径，不能假定会自动继承聊天模型或额度 |
| 简易切本地与上下文诊断 | 不在当前范围 | 后续验证；接口预留，不现在安装/切换模型 |

## 四、建议的融合方案

保留 Rust CLI 和 provider/preprocessing/report 等模块，在其中建立一条处理链：
扫描配对 → 识别比较组/保护序列 → 生成概览与细节 → 单张分析及组内比较 → 持久保存审阅决定 → 暂存写回计划 → 检查冲突后应用 → 读回核验/可回滚。

“单张评分”可以作为辅助数据继续存在，不能直接等同最终星级和色标。现有 provider 接口可扩展为多图输入，添加受约束的结构化比较结果；不需重写所有 API 适配器。暂不决定 SQLite 还是文件日志，先定义数据与状态转换、恢复要求，再按实现复杂度选择。JSON 交换文件可以服务当前 Codex 直接审阅与将来独立本地批处理。

旧新加坡脚本用于提取经过现场验证的处理行为与测试样例：Rating/Label 限定修改、JPEG 其他分段/像素数据保持、中文色标、哈希、暂存与回滚。其路径绑定、重复暂存会覆盖备份、单一事务状态中断恢复不完备、用 assert 做关键保护等不能原样迁移。真实照片、侧车、私有路径和目录数据库都不提交 GitHub。

PR #1 的选片规则可以整理后复用；Python ledger 先不合并为长期产品架构。它目前也没有按字节记录图片/元数据版本或自动验证实际看图，测试通过只说明结构约束通过。最终在 Rust 主程序统一任务状态，避免两套状态源。

## 五、版本管理与实施顺序

- main 保持上游基线；审计在独立分支与草稿 PR，PR #1 保持未合并。
- 第一批：仅元数据安全修复与对应回归测试，先不加新审美判断。
- 第二批：配对扫描、方向处理、结果有效性与错误状态；建立同一程序的分析/应用分离和续跑机制。
- 第三批：加入组内比较、保护序列、个人星级/红绿规则，先在少量副本上评测。
- 第四批：完成 Lightroom 实际读回与 JPEG-only 兼容验证，之后才扩到图库；本地模型切换/精度另行评测。
- 每批一个目的明确的 PR，固定基线、测试记录和回退方法；规则版本、模型版本和程序提交号写进运行记录。程序版本不替代每次写回的独立备份。
- 不因“已 Fork”或“已有代码”而强行继续：如果第一批不能用清楚、可测试的小改动建立可靠写回边界，或维护成本明显高于一个更小的专用实现，应停止并带具体比较结果讨论是否重写。目前尚无足够证据支持放弃全部 imgcull。

## 六、需要与用户确认的处理取舍

1. 推荐默认先完成并保存审阅，再集中写回，不一边等待模型一边改源文件；这是为已有调色和游戏时后台运行服务，会增加暂存空间。
2. 人工星级/色标遇到 AI 不同意见：推荐保留原值，并在报告中提示建议，不悄悄更改。
3. 第一版的执行入口：推荐先支持“当前 Codex 看图并提交决定”，同时保持可插入 Ollama 的接口；若直接让 Rust 自己调用云模型，需要另行 API 配置，不能假定沿用当前聊天的登录方式。
4. PR #1 中新增的 Python 记录机制推荐不作为正式架构合并，保留其规则和有用测试意图，在 Rust 主流程内统一实现。

这些是下一步设计讨论，当前审计没有擅自实施以上取舍。
